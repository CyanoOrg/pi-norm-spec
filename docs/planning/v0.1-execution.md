# v0.1 Initial Rust-backed Adapter Execution Plan

Goal: ship a self-contained Rust-backed pi adapter with a minimal, typed
ExtensionAPI entry point and no duplicated `.norm` format semantics.

## Gate A — Bootstrap

- [x] Establish repository governance.
- [x] Record the hybrid adapter and upstream-authority decisions.
- [x] Define Rust engine and bridge crates.
- [x] Add the TypeScript extension entry skeleton.
- [x] Add protocol fixtures and CI gates.
- [x] Establish the independent public `0.1` product line.

## Gate B — Upstream contract

- [x] Select the norm-spec CLI machine boundary and pin the initial public
      product plus exact compatibility identities (D005).
- [x] Define a release-derived, platform-specific payload that includes the
      complete conformance inputs and has no implicit `PATH` fallback (D006).
- [x] Resolve the matching payload for norm-spec `0.1.0-rc.1` and verify its
      checksum, manifest source revision, and declared identities.
- [x] Reject incompatible protocol versions with a stable error.
- [x] Consume compatibility, collect, and validate machine responses without a
      parser, filesystem-walk, or empty-ruleset fallback.
- [x] Exercise all 82 cases from the exact upstream contract bundle without
      skip-on-error behavior.
- [x] Confirm the same payload/identity/conformance path on all four native
      hosted targets for the exact Gate B candidate.

## Gate C — Runtime bridge

- [x] Measure short-lived versus persistent pi bridge latency, cancellation,
      crash isolation, and packaging while keeping the D005 upstream CLI
      boundary fixed.
- [x] Record the chosen pi bridge lifecycle model (D008).
- [x] Implement JSON/JSONL framing, IDs, cancellation, and graceful shutdown.
- [x] Surface startup and crash failures to the extension.
- [x] Confirm the exact Gate C candidate's Rust server, TypeScript client, and
      public payload lifecycle on all four hosted targets.

## Gate D — pi behavior

- [x] Implement per-turn path-scoped convention collection.
- [x] Inject structured summaries without persisting them in session history.
- [x] Add the single pi-specific Skill and one-notice zero-`.norm` onboarding
      path from D007 without automatic project writes.
- [x] Complete a functional Alpha checkpoint with real install, handshake,
      collection, cold-start, and ephemeral-injection evidence.
- [x] Record the exact machine-evaluable enforcement subset as empty for the
      pinned contracts; natural-language conventions remain prompt guidance
      (D010).
- [x] Keep blocking disabled while the declared hard-enforcement subset is
      empty.
- [ ] Reopen typed enforcement only after norm-spec owns operation semantics
      and pi guarantees the final evaluated input plus documented per-call
      parallel clearance and dispatch behavior.
- [ ] Implement the approved exact-call escape together with typed enforcement.
- [x] Define successful built-in `write`/`edit` post-validation as bounded,
      serialized soft feedback without blocking or rollback (D011).
- [x] Surface canonical post-edit validation findings and failures through the
      final tool result while preserving the original result state.
- [x] Confirm post-edit feedback through the real pi host and package-shaped
      installation on every native target.

## Gate E — Distribution and release

- [x] Define the production five-package topology, exact optional dependency,
      release-manifest, artifact, installation, and beta-rehearsal contract
      without publication authority (D012).
- [x] Add source-controlled root/platform publish manifests, strict release
      identity validation, glibc-aware selection, and the bundled executable
      launcher (E1 implementation).
- [x] Confirm the exact E1 branch candidate through hosted Rust, Extension,
      Linux, macOS ARM/Intel, and Windows jobs before starting E2.
- [x] Implement clean-revision root/native package staging, retained tarballs,
      checksums, and exact five-package aggregate verification without
      publication credentials (E2 implementation).
- [ ] Confirm one root plus four native package candidates, all ten checksum-
      bound files, and the aggregate inventory from one exact revision through
      hosted CI (E2 closure).
- [ ] Run isolated version-pinned `pi install`, injection, Skill, onboarding,
      post-edit feedback, bundled-CLI, and negative package/runtime tests on all
      four native targets (E3). Do not require or claim hard blocking.
- [ ] Complete release-quality and security review.
- [ ] Prepare and host-verify the exact `0.1.0-beta.1` candidate.
- [x] Execute the separately approved public-visibility checkpoint with
      protected `main`, immutable `v*` tags, restricted Actions, and private
      vulnerability reporting (D013).
- [ ] Execute the signed tag, GitHub Pre-release, and five-package npm
      publication only at their separate maintainer checkpoints (E4).
- [ ] Promote stable `v0.1.0` only after public beta validation and a separate
      maintainer decision.

## Human checkpoints

Upstream version pinning, process model, escape semantics, public alpha, and
stable publication require maintainer approval.
